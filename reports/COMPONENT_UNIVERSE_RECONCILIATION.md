# Component Universe Reconciliation (v1.2, CMP-02)

*Single source of truth for the paper's headline SAD-CODE `component_f1`.*

This artifact records the **definition change** (D-01/D-02) that makes the
mapped-only component universe canonical, the **measured old→new delta** (D-02),
and the **supersession ledger** (D-03/D-04) accounting for every in-repo artifact
that carried the old number. Phase: `07-suite-universe-reconciliation`, plan `07-02`.

## 1. What changed (definition, not source)

`metrics_api._compute_component_f1` (`src/bias/evaluation_critique.py`) previously
added a per-file `{b}` singleton fallback: a `(sentence, file)` pair whose file maps
to **no** SAM-CODE component was kept as a `(sentence, file)` pseudo-component in both
gold and result. As of v1.2 that fallback is **removed** — files with no SAM-CODE
mapping are **dropped**, mirroring `component_suite._code_inputs`. The headline
`component_f1` is now the **mapped-only micro** number and equals `component_suite`
`micro` for the same project **by construction** (asserted to 1e-6 in the Task-1
verify and in `mini-src/check.py` to 1e-9).

Per D-02 this is a **definition change**, not a result-source change: the canonical
input is the bundled in-repo `results/` tree (default TransArc layout). The older
standalone `reports/metrics_sad-code.csv` value (`0.732`, scored from a different
result source) is simply **overwritten** by re-running the generator against the
bundled results — one definition + one bundled input = one set of numbers. No
source archaeology.

## 4. Incidental: SAD-SAM metrics refresh (blocking-issue fix, Rule 3 — NOT D-01)

Two pre-existing staleness issues surfaced when the plan-mandated generators
(`metrics_api.py --task sad-sam`, `rq1_panels.py`) were run against the **current**
bundled `results/` tree. None of these are caused by the D-01 component-universe
change (SAD-SAM `component_f1` collapses onto link F1 and is unchanged); they are the
generators re-aligning stale committed SAD-SAM outputs to the current bundled results
(D-02 single-source-of-truth; CLAUDE.md "keep reports consistent with the script that
produces them"). Generator-based regeneration — never a silent overwrite.

1. **`reports/metrics_sad-sam.csv` was a stale empty placeholder** (only an em-dash
   `Average` row), which made `src/paper/generate_tables.py` **crash** (`could not
   convert string to float: '—'`) in `t_converged_framework`/`t_consequences`. The
   plan's own Task-2 verify requires `generate_tables.py` to exit 0, impossible against
   an empty SAD-SAM CSV, so it was repopulated via
   `python3 src/lib/metrics_api.py --task sad-sam`. This restores the populated state
   the committed `consequences.tex`/`converged_framework.tex` SAD-SAM rows were already
   built from. Side effect: SAD-SAM **Sentence F1** in `consequences.tex` refreshed
   (AVG 0.875 → 0.825). Touched (not in plan scope): `reports/metrics_sad-sam.csv`,
   `writing/tables/metrics_sad-sam.tex`.

2. **The agent-linker (`aalinker-*`) `rq1_panels.py` panels were stale** vs. the
   current bundled agent-linker results, on **both** tasks:
   - SAD-SAM (no `component_f1` column, so the shift is provably **not** D-01):
     `reports/rq1/aalinker-claude_sad-sam.csv` (link_f1 AVG 0.9389 → 0.9386) and
     `reports/rq1/aalinker-openai_sad-sam.csv` (link_f1 AVG 0.9218 → 0.9037).
   - SAD-CODE: `reports/rq1/aalinker-claude_sad-code.csv` and
     `aalinker-openai_sad-code.csv` moved on **file-level** metrics too
     (e.g. aalinker-claude file_f1 AVG 0.9387 → 0.9157), which D-01 does **not**
     touch — confirming these panels were re-aligned to newer bundled agent-linker
     results, with the `component_f1` shift (0.8846 → 0.8979) being a mix of that
     refresh and the mapped-only definition.

   The **D-01-only** SAD-CODE panels (transarc, artemis, lissa, lissa-gpt4omini)
   moved on `component_f1` alone with `file_f1` byte-identical, and all SAD-SAM
   panels except the two `aalinker-*` ones regenerated byte-identical.

## 5. Determinism note (pre-existing, deferred)

`reports/SADCODE_S11_S13F_VS_TRANSARC.csv` is **not** byte-identical across runs: only
the `*_ndg` columns (`transarc_ndg`, `s11_ndg`, `s19_claude_ndg`, `s19_openai_ndg`)

concern — are fully deterministic and stable across runs.
