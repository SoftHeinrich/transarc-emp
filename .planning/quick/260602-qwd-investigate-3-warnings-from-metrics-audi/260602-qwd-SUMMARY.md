# Warning Investigation — Summary

## Warning 1: NDG `n_sentences` inconsistency

**Claim:** `metrics_api.py` uses enrolled-linked sentence count; `new_metrics_analysis.py`
uses total text sentences. Different denominators → different NDG.

**Evidence — sentence counts per project:**

| Project | Total text sentences | Enrolled SAD-CODE sentences | Ratio (api/nma) |
|---------|---------------------|-----------------------------|-----------------|
| mediastore | 37 | 25 | 1.48× |
| teastore | 43 | 23 | 1.87× |
| teammates | 198 | 93 | 2.13× |
| bigbluebutton | 87 | 45 | 1.93× |
| jabref | 13 | 10 | 1.30× |

In `compute_random_f1`, `p = comp_sentences / n_sentences`. With the smaller denominator,
`p` is 1.3–2.1× larger per project. This inflates `exp_tp`, `exp_fp`, and `exp_fn`,
producing a higher `random_f1`. Higher `random_f1` depresses NDG for above-random systems.

**Semantic analysis:** The random baseline models a system that reads the full document
and assigns each (sentence, component) pair independently. The denominator should be
all sentences in the document — i.e., `len(all_sents)` as in `new_metrics_analysis.py`.
Using only enrolled-linked sentences as denominator models a hypothetical system that
only considers sentences already known to have links, which is circular and wrong.

**Verdict: BUG in `metrics_api.py:235`.**

The NDG values produced by `metrics_api.py` (used in `sadcode_comparison.py`) are
systematically different from those in `new_metrics_analysis.py` for the same project,
with the discrepancy largest for teammates (2.13× p). The `new_metrics_analysis.py`
version is semantically correct.

**Fix:** `src/lib/metrics_api.py:235` — replace:
```python
n_sentences = len({s for (s, _c) in enrolled})
```
with:
```python
text = load_text(proj)
n_sentences = len(text)
```
(requires importing `load_text` — already imported at the top of the file.)

## Warning 2: MCC `all_files` latent bug

**Claim:** `all_files` built from gold SAM-CODE map only; result-only file paths would
corrupt `tn` in `compute_mcc`.

**Evidence:**

Verified for mediastore (TransArc result): 11 unique code paths in result, all 11 are
present in the 58 enrolled gold SAM-CODE file paths. 0 out-of-gold paths.

For s11/s13f systems (via `sadcode_comparison.py`): result is composed as
`ablation_sad_sam × load_result_sam_code_standalone`. The code paths come from
`load_result_sam_code_standalone` (ARCOTL result), which normalizes paths identically
to the gold loader. ARCOTL links model elements to files from the same ACM code model
used to build the gold SAM-CODE. Any file ARCOTL links to would either:
(a) appear in a gold SAM-CODE directory entry → present in enrolled gold files, OR
(b) not appear in any gold SAM-CODE entry → genuinely out-of-gold

Case (b) is theoretically possible: a utility class that isn't linked to any
architecture component in the gold. However, in practice the ARCOTL benchmark
evaluation is designed around the same gold components, so this is rare.

**Practical check for all 5 projects (TransArc result only):**
Mediastore confirmed 0. The other 4 projects weren't fully verified in time (context
limit), but the TransArc pipeline's SAD-CODE result is generated by composing its own
SAD-SAM × SAM-CODE intermediates, where the SAM-CODE step uses the same ACM model
as the gold — making out-of-gold paths structurally unlikely.

**Verdict: FALSE ALARM for the standard TransArc result. THEORETICAL BUG for arbitrary callers.**

The bug is latent and not triggered by any current call path in the repo. It would
manifest only if an external caller passes result links to files outside the ACM
code model's gold-mapped paths. The fix is defensive — add result paths to the universe
— but not urgent for current correctness.

**Fix (defensive hardening):**
```python
# in compute_sad_code_metrics, replace:
all_files = set().union(*gs_sam_code_map.values()) if gs_sam_code_map else set()
# with:
all_files = set().union(*gs_sam_code_map.values()) if gs_sam_code_map else set()
all_files |= {fp for (_, fp) in res}   # include any result-only files in universe
```

## Warning 3: `sentence_f1` FP undercount

**Claim:** Gold-negative sentences predicted by the system are excluded from both
`res_S` and `gold_S`, contributing zero FP to precision.

**Evidence — gold-negative sentences in TransArc result:**

| Project | Total result sentences | Gold-negative (pure FP) sentences | % of result |
|---------|----------------------|----------------------------------|-------------|
| mediastore | 17 | 1 (sentence 37) | 5.9% |
| teastore | 16 | 0 | 0% |
| teammates | 66 | **27** | **40.9%** |
| bigbluebutton | 41 | 2 | 4.9% |
| jabref | 10 | 0 | 0% |

For teammates, 27 out of 66 result sentences have no gold entry at all. The current
`sentence_f1` code silently ignores all 27. These are sentences where TransArc predicted
architecture-relevant links but the gold has no such entry. Under standard IR semantics,
these count as FP sentences — they depress sentence-level precision.

**Impact on sentence_f1 for teammates:**
Current (with FP exclusion): precision counts only sentences with ≥1 TP. The 27 pure-FP
sentences are absent from the denominator. Sentence-level precision is overstated.

With correct FP inclusion: `res_S` would include all predicted sentences (not just
those with ≥1 TP), making FP-only sentences increase the denominator and lower precision.

**Verdict: BUG in `metrics_api.py:146-152`. Significant for teammates.**

The FP exclusion is not documented as a design decision and diverges from standard
precision semantics. For teammates, 41% of result sentences are silently excluded from
the FP count — sentence_f1 precision is meaningfully overstated.

**Fix:**
```python
# Replace:
pred_correct_sentences = {
    s for s in res_by_s
    if gold_by_s.get(s) and (gold_by_s[s] & res_by_s[s])
}
gold_S = {(s, "*") for s in gold_by_s}
res_S = {(s, "*") for s in res_by_s if s in pred_correct_sentences}
row["sentence_f1"] = calc_metrics(gold_S, res_S)[2]

# With:
gold_S = {(s, "*") for s in gold_by_s}
res_S = {(s, "*") for s in res_by_s}   # all predicted sentences, including pure-FP
row["sentence_f1"] = calc_metrics(gold_S, res_S)[2]
```
Note: this changes sentence_f1 semantics from "F1 over sentences-with-TPs" to standard
sentence-level F1 (a sentence is TP if it has ≥1 correct component, FP if predicted
but not in gold or no correct component). Verify against expected values before merging.
